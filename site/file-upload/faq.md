# File Upload: Technical FAQ

## Validation

### Why not trust the `Content-Type` of the part?
The client sets it. The server uses the extension and the bytes.

### Why is the file name compared exactly?
The name is generated by the system from the Idea, so any difference is a user error the client can fix. The failure response carries the expected name.

### A user sees "mismatch" but the names look identical. Why?
Usually Unicode normalization (NFD from macOS) or a lookalike character. The server normalizes to NFC before comparing, so a remaining mismatch is a real difference such as a full-width underscore or a trailing space.

### Why is the size limit exactly 5 MiB and not "about 5 MB"?
MiB is 1,048,576 bytes. The validator uses 5,242,880 so the boundary is testable: a file of that size passes, one byte more fails.

### Why is a zero-byte file a different error from a bad type?
`EMPTY_FILE` tells the user the file is empty, which is usually a failed export. A zero-byte file would also fail the magic check, but that message would be misleading.

## Security

### Does the PPTX check make the file safe?
No. It checks that the file is a ZIP with two expected entries. Macros, embedded objects and links are not examined. Treat uploaded files as untrusted when opened.

### Can a zip bomb hurt the server?
The server reads the central directory only and never extracts entries, and the body is capped at 5 MiB. The risk is on the machine that opens the file.

### Can a user choose where the object is stored?
No. The key is built from the Idea id and a random UUID. The user's file name is only compared with the expected name and recorded in audit metadata.

### Why is the file name taken as sent, without `filepath.Base`?
`Base` would strip path components such as `../` and hide an invalid name. The rule wants to reject them, not clean them.

### Why are role and state checked before the body is read?
So a caller who may not upload cannot make the server read and spool megabytes.

## Consistency

### What if MinIO is down?
`Put` fails after the 2 s dial timeout and one retry; the client gets `503 STORAGE_UNAVAILABLE`. No database row changed.

### What if the upload succeeds but the database fails?
The outcome decides. Known rollback: delete the new object now, or record it if that fails. Unknown outcome: keep it and record it with a 10-minute delay, because the commit may have succeeded.

### Why is an object kept after an unknown outcome?
Deleting an object that a committed row references would leave a broken Idea. An orphan is cheaper than a broken record.

### What happens to the old file after a replace?
It is recorded in `pending_file_deletion` inside the same transaction, then deleted after commit. If the delete fails, the row stays for the clean-up job.

### Two replaces at the same time?
The transaction locks the Idea row, so they are serialized. The loser's object is compensated. A test, `TestReplaceSlidesConcurrentLeavesNoOrphan`, covers it.

### Can a retry duplicate a file?
It can leave an orphan object, never a second reference: each attempt has its own key and only the committed one is referenced.

## Operations

### Why does a large upload fail with an HTML 413 sometimes?
The ingress limit (6 MiB) can reject before the app does. Its body is not the application's JSON problem format. Clients must handle both.

### The pod's temp disk filled up. What do we check?
The `/tmp` `emptyDir` size limit (about 256 MiB) versus peak concurrent uploads. Temp files are removed on every path, so a leak points to a crash mid-request.

### How do we find orphaned objects?
Look at `pending_file_deletion` for due rows, and compare listed object keys with `idea` rows. The clean-up job that automates this is not implemented yet.

### What should we monitor?
Rate of `FILE_TOO_LARGE`, `UNSUPPORTED_FILE_TYPE` and `STORAGE_UNAVAILABLE`; the count and age of pending rows; temp-disk usage.

## Testing

### How do I test a new rule?
Add a case to `TestValidate`. If it changes the response, add a case to the integration tests for create and replace.

### How do I test the unknown-outcome path?
The fault-injection tests (`TestReplaceSlidesLostCommit` and `TestDeleteIdeaLostCommit`) simulate a lost COMMIT.
